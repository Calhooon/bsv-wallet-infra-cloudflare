(`bsv-stack-lean` `docs/charters/storage.md:36`.)

**The cross-store write.** Today `processAction` writes `transactions` and `outputs` in one D1 batch (`src/storage/process_action.rs:281-393`; `src/d1/batch.rs:1-9`) and then the req by separate awaited statements after it (:396-486: a select by txid, then an `UPDATE` or an `INSERT` and a second `UPDATE` for `input_beef`); a fault between the two leaves the wallet's rows without their req today `[SRC]`. (The two-statement batch at :732-735 is another function, `update_transaction_status_after_broadcast` at :663.) After the split the object's step commits the wallet's rows and an `outbox` row in one transaction; after the commit the object upserts the req into D1 by txid and deletes the outbox row; a failed upsert stays in the outbox and the alarm retries it, so the design is no weaker than today's and closes today's gap. The upsert keeps today's guard (:425-436: a req at `completed`, `unmined` or `unproven` keeps its status and takes only `raw_tx` and `input_beef`): `INSERT ... ON CONFLICT(txid) DO UPDATE SET raw_tx = excluded.raw_tx, input_beef = excluded.input_beef, updated_at = excluded.updated_at, status = CASE WHEN proven_tx_reqs.status IN ('completed','unmined','unproven') THEN proven_tx_reqs.status ELSE excluded.status END`, so a late outbox retry never knocks a completed req back. The req is the tracker's hint, never the wallet's truth, so a late req delays a broadcast retry and writes no word `[D]`.

**Ancestry for a BEEF.** Today's three tiers (`create_action.rs:1181-1394`: `proven_txs`, `transactions`, `proven_tx_reqs`) become: the object's own rows, then R2 `proofs/{txid}` through the D1 index, then the D1 req (`raw_tx`, `input_beef`), then the network. An unproven parent made by another wallet on this server is still found in the D1 req `[D]`; a witness pins it (part 10, L5).

## 6. The migration tool: 402 wallets from D1 into objects

| step | the act |
|---|---|
| freeze | the release that routes to objects stops every D1 write to a wallet table; D1 is the frozen source from the deploy's minute; the old version stays deployable |
| move (lazy) | a wallet's next door call reaches its object; an object with no `meta.moved` row sets an in-memory `moving` flag (calls meanwhile answer `STORE_BUSY`), reads the wallet's rows from D1 by `user_id` (awaits, nothing written yet), then writes them in one `transactionSync` step keeping every primary key, sets each `sqlite_sequence` to the D1 table's max id (no id collides with a moved blob key), and writes `meta.moved` with the D1 digest |
| move (idle) | the tool walks the D1 index for wallets not moved in 7 days `[EST]` and opens each with a location hint (Q3); same step |
| the proof | `digest = sha256` over 13 tables in this order: `users`, `certificates`, `certificate_fields`, `output_baskets`, `transactions`, `commissions`, `outputs`, `output_tags`, `output_tags_map`, `tx_labels`, `tx_labels_map`, `sync_states` (the 12 per-wallet tables of 0001), then the wallet's share of `proven_txs` in the object's columns (`proven_tx_id`, `txid`, `height`, `idx`, `block_hash`, `merkle_root`, `merkle_path`); `settings` is not in it (a copy of the server's row). Rows by primary key, columns in schema order, each value as a type tag plus its bytes, R2 blobs by key plus their sha256. In D1 the rows are selected by `user_id` where the table has it; the two maps and `proven_txs` have none (0001_initial.sql:8-19, :197-202, :225-230), so: `output_tags_map m JOIN output_tags t ON t.output_tag_id = m.output_tag_id WHERE t.user_id = ?`, `tx_labels_map m JOIN tx_labels l ON l.tx_label_id = m.tx_label_id WHERE l.user_id = ?`, and `SELECT DISTINCT p.* FROM proven_txs p JOIN transactions t ON t.proven_tx_id = p.proven_tx_id WHERE t.user_id = ?`. Computed in D1 and in the object; refused unless equal; both written to `moves/{identity}/{run}.json` and to `users.digest` |
| rollback | while D1 is frozen: redeploy the old version for a wallet whose object took no write after the move (`meta.writes = 0`); for one that did, the reverse mover writes the object's rows back to D1 in batches of 100 statements (`src/d1/batch.rs:4`) with `users.state = 'returning'` as the guard the old code refuses, then the digest again |
| keep | the D1 rows stay until 30 days `[EST]` after the last wallet moved and the read-only measurement below is green |

**The read-only measurement that proves nothing was lost** (the method of `docs/READINESS-2026-10-26.md` section 4: `SELECT` counts through the D1 query API, the analytics datasets): before, the row counts of the 16 tables (section 4's table); after, the sum over the 402 objects of each wallet table's count equals the D1 count, `users.digest` equals the object's digest for every wallet, and the R2 key count of `BLOBS` is unchanged. The evidence goes under `/Volumes/Lanes/out/bsv-wallet-infra-cloudflare-public/`; no id or key on the page.
