**The prefix bound to the server's identity.** The HMAC is keyed by the server's key, and the payer derives the output key with the server's identity key as counterparty (`AuthFetch.ts:873-877`), so a quote redeems only here and the output only this key spends `[SRC]`.

**The quote window and the floor** `[D]` (the captain's ruling). A wallet whose active storage is this server builds its top-up through this server: `createAction` (`AuthFetch.ts:885`) is itself a storage call, which would meet a 402 and recurse. The floor exists only for that: issuing a 402 sets `quote_until = now + 120 s` on the account, and while it holds a priced call without a payment is served with the balance allowed down to -1,000 sats. The floor is 10 calls `[EST]`: it is not measured against how many storage calls a wallet makes to build its payment (`createAction`, `processAction`, any `internalizeAction` of coin it receives); W7 counts them. Past the floor, or below 0 outside the window, a priced call without a payment answers the 402 quote; nothing is served free. A deposit (an `internalizeAction`, or any call, that carries a valid BRC-105 payment to the operator) is never refused with a 402: the credit is applied before the call's debit, in the same transaction, so the call is then served and debited. So that a deposit always lands its call at or above the floor, the quote asks the call's price plus 1,000 when that exceeds 10,000 (a batch commit of more than 90 actions).

| the account | the call | what the client sees |
|---|---|---|
| allowance at least n, or balance minus price at least 0 | priced, no payment | served; debited n calls or the price |
| the window open, balance minus price at least -1,000 | priced, no payment | served into the floor |
| otherwise | priced, no payment | the signed 402 quote; the window (re)opens; nothing served |
| any | a valid payment to the operator | credited, served, debited; 200 with `x-bsv-payment-satoshis-paid` |
| any | an invalid or replayed payment | section 3's 400 or 409; nothing credited, nothing served |
| debited | the server faults (`-32603` or a 5xx) | the fault; the debit refunded |
| debited | the client's error (`-32602`, `-32001`, method not found, a 4xx) | the error; charged |

Both transports feed step 4 unchanged (amendment lines 94-96); the handler sees only the `body` part.

## 2. The credit ledger

**The home.** Final: the wallet's own object in `bsv-wallet-store` (named by the owner's word of 2026-10-27 13:0xZ; `Calhooon/bsv-wallet-store` at 9536364, the executor its #5), keyed by identity (#28), tables `credit_accounts` (one row there) and `credit_topups`. Interim, until #28 lands: the global D1 `DB`, the same two tables keyed by `identity_key`. The statements are identical in both homes `[D]`.

```sql
CREATE TABLE credit_accounts (
  identity_key    TEXT PRIMARY KEY,
  allowance_calls INTEGER NOT NULL,
  balance_sats    INTEGER NOT NULL DEFAULT 0,
  quote_until     INTEGER NOT NULL DEFAULT 0,
  calls_served    INTEGER NOT NULL DEFAULT 0,
  last_debit_calls INTEGER NOT NULL DEFAULT 0,
  updated_at      INTEGER NOT NULL DEFAULT (unixepoch()));
CREATE TABLE credit_topups (
  txid TEXT PRIMARY KEY, identity_key TEXT NOT NULL, satoshis INTEGER NOT NULL,
  derivation_prefix TEXT NOT NULL, created_at INTEGER NOT NULL DEFAULT (unixepoch()));
-- onboarding: in the same batch as the debit, a no-op once the row exists
INSERT INTO credit_accounts (identity_key, allowance_calls) VALUES (?1, 1000)
  ON CONFLICT(identity_key) DO NOTHING;
-- the debit, a priced call without a payment: one conditional UPDATE, the floor in its WHERE
-- ?2 = the price in sats, 100 x n; ?3 = n (1, or the actions of a batch commit)
UPDATE credit_accounts SET
  allowance_calls  = allowance_calls - CASE WHEN allowance_calls >= ?3 THEN ?3 ELSE 0 END,
  balance_sats     = balance_sats - CASE WHEN allowance_calls >= ?3 THEN 0 ELSE ?2 END,
  last_debit_calls = CASE WHEN allowance_calls >= ?3 THEN ?3 ELSE 0 END,
  calls_served     = calls_served + 1, updated_at = unixepoch()
WHERE identity_key = ?1 AND (allowance_calls >= ?3 OR balance_sats - ?2 >=
  CASE WHEN quote_until > unixepoch() THEN -1000 ELSE 0 END)
RETURNING last_debit_calls, allowance_calls, balance_sats;
-- no row returned: the 402 quote, and the window opens
UPDATE credit_accounts SET quote_until = unixepoch() + 120 WHERE identity_key = ?1;
-- a deposit (a call carrying a valid payment): credit, then the call's debit, ONE transaction
-- (a D1 batch; in the object one transactionSync); the PRIMARY KEY makes it once per txid
INSERT INTO credit_topups (txid, identity_key, satoshis, derivation_prefix) VALUES (?4, ?1, ?5, ?6);
UPDATE credit_accounts SET balance_sats = balance_sats + ?5, quote_until = 0 WHERE identity_key = ?1;
UPDATE credit_accounts SET
  balance_sats = balance_sats - ?2, last_debit_calls = 0,
  calls_served = calls_served + 1, updated_at = unixepoch()
WHERE identity_key = ?1
RETURNING last_debit_calls, allowance_calls, balance_sats;
-- the refund, a server fault only: what the debit took, read from its RETURNING
-- ?3 = last_debit_calls; ?2 = the price when that is 0, else 0
UPDATE credit_accounts SET allowance_calls = allowance_calls + ?3,
  balance_sats = balance_sats + ?2, calls_served = calls_served - 1,
  updated_at = unixepoch() WHERE identity_key = ?1;
```

SQLite evaluates every `SET` expression on the row's old values, so the three `CASE`s see the same state, and `RETURNING` gives the row as updated, so `last_debit_calls` names what this debit took `[X]` (sqlite3 3.51.0, 2026-10-27: a batch commit of n = 2 with 2 calls left took 2 calls and 0 sats and its refund gave back exactly that; n = 3 with 2 calls left and no balance returned no row; in the window ten 100-sat calls served from 0 to -1,000 and the eleventh returned no row; a deposit of 10,000 at -1,000 with a 100-sat call left 8,900; the same txid again refused by the PRIMARY KEY). The debit runs before dispatch, and its condition stays in the `WHERE` in the object home too: two calls can interleave across an await (the payment's verify, the dispatch), so the single writer alone would not stop both spending the last 100 sats `[D]`. A deposit's debit carries no floor: the ruling says it is served, and the quote's size (section 1) keeps it at or above 0, since the quote is the greater of 10,000 sats and the call's price plus 1,000, so a paid deposit's debit never ends below 0.

**The refund, precisely.** Only a server fault is refunded: a JSON-RPC `error` of code `-32603` (the store's `DatabaseError` and `InternalError`, `src/dispatch.rs:137-138`) or a 5xx after the debit; the refund commits before the answer is signed. A client's error is charged: `-32602` (`ValidationError`, `:135`), `-32001` (`NotFound`, `:136`), method not found (`:127`), any 4xx; each still costs the auth check, its reads and the row writes, so a free failing call would be an unmetered path (T4). The refund gives back what the debit took, from its `RETURNING`: n allowance calls, or 100 x n sats, never another unit, so a failed batch commit returns what it cost and mints nothing `[D]`. A refund that fails to commit writes one `monitor_events` row (`credit_refund_fault`, the identity, the request nonce) for the operator's manual credit; the scoreboard's target for that row is 0. A Worker that dies between debit and refund loses the payer 100 sats; the object home narrows this to the object's own crash `[D]`.

**The reconciler** `[D]`. A payment the operator took in but did not credit is otherwise lost to the payer. The cron (`wrangler.toml:86`), on every run (in the object home, the operator object's alarm), compares the operator's `storage credit` outputs in this store with `credit_topups`:

```sql
SELECT o.txid, o.satoshis, o.sender_identity_key, o.derivation_prefix
FROM outputs o
JOIN tx_labels_map m ON m.transaction_id = o.transaction_id AND m.is_deleted = 0
JOIN tx_labels l ON l.tx_label_id = m.tx_label_id AND l.user_id = ?1 AND l.label = 'storage credit'
LEFT JOIN credit_topups c ON c.txid = o.txid
WHERE o.user_id = ?1 AND o.vout = 0 AND c.txid IS NULL
  AND julianday(o.created_at) < julianday('now', '-300 seconds')
LIMIT 100;
```

Each row is credited late in one batch: section 2's deposit without the call's debit (the `INSERT` into `credit_topups`, whose PRIMARY KEY loses any race with the door, and the balance `UPDATE`), plus the accounting row `monitor_events` (`credit_late`, the identity, the txid, the sats). Five minutes of age keeps it off a call still in flight.

## 5. The public shape

**The price page** (text for the keeper to publish, rule 14):

> Wallet storage on Cloudflare. Every identity starts with 1,000 calls free. After that a call costs 100 satoshis, paid in advance: when your credit runs out the server answers with a standard BRC-105 402 asking 10,000 satoshis, which your wallet pays by itself (100 calls of credit). The connection handshake, the settings reads and the calls that release a reservation are free; a batch commit costs one call per action; a call the server fails is not charged, a call refused for its own request is; a deposit is never refused for lack of credit. Payments go to the server's identity key; credit is not refundable in coin and does not expire. Prices may change with 30 days' notice on this page.

**The 402 is the quote**: its headers and body (section 1) are the whole tariff a client needs; no other endpoint carries a price.

**The terms line**: "Credit buys calls at the posted price; it is not a deposit, carries no interest and is not redeemable for coin; the operator keeps the right to refuse abuse under the posted rate limits." (the keeper's and the owner's words, rule 14).
