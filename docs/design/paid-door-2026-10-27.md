**The prefix bound to the server's identity.** The HMAC is keyed by the server's key, and the payer derives the output key with the server's identity key as counterparty (`AuthFetch.ts:873-877`), so a quote redeems only here and the output only this key spends `[SRC]`.

**The quote window** `[D]`. A wallet whose active storage is this server builds its top-up through this server: `createAction` (`AuthFetch.ts:885`) is itself a storage call, which would meet a 402 and recurse. So issuing a 402 sets `quote_until = now + 120 s` on the account; while it holds, calls are served with the balance allowed down to -1,000 sats (10 calls), enough for the payment's `createAction` and `processAction`. `internalizeAction` is always served into the same floor without a 402 (a deposit is how a wallet pays). Below the floor every priced call is a 402.

**Multipart.** The reference client always sends the header (`AuthFetch.ts:792-796`); the crate's x402 helper switches to multipart above 8,192 bytes of payment JSON (`multipart.rs:3-4, 84`) `[SRC]`; the amendment's motivation is about 16 KB per header value at Cloudflare (amendment line 24), and the client's own note is 32 KB of total headers (`AuthFetch.ts:110-111`). Both transports feed step 4 unchanged (amendment lines 94-96); the handler sees only the `body` part.

## 2. The credit ledger

**The home.** Final: the wallet's own object in `bsv-wallet-store` (working name until the owner's word), keyed by identity (#28), tables `credit_accounts` (one row there) and `credit_topups`. Interim, until #28 lands: the global D1 `DB`, the same two tables keyed by `identity_key`. The statements are identical in both homes `[D]`.

```sql
CREATE TABLE credit_accounts (
  identity_key    TEXT PRIMARY KEY,
  allowance_calls INTEGER NOT NULL,
  balance_sats    INTEGER NOT NULL DEFAULT 0,
  quote_until     INTEGER NOT NULL DEFAULT 0,
  calls_served    INTEGER NOT NULL DEFAULT 0,
  updated_at      INTEGER NOT NULL DEFAULT (unixepoch()));
CREATE TABLE credit_topups (
  txid TEXT PRIMARY KEY, identity_key TEXT NOT NULL, satoshis INTEGER NOT NULL,
  derivation_prefix TEXT NOT NULL, created_at INTEGER NOT NULL DEFAULT (unixepoch()));
-- onboarding: in the same batch as the debit, a no-op once the row exists
INSERT INTO credit_accounts (identity_key, allowance_calls) VALUES (?1, 1000)
  ON CONFLICT(identity_key) DO NOTHING;
-- the debit, per priced call (?2 = 100; ?3 = 1 for internalizeAction, else 0)
UPDATE credit_accounts SET
  allowance_calls = allowance_calls - (allowance_calls > 0),
  balance_sats    = balance_sats - CASE WHEN allowance_calls > 0 THEN 0 ELSE ?2 END,
  calls_served    = calls_served + 1, updated_at = unixepoch()
WHERE identity_key = ?1 AND (allowance_calls > 0 OR balance_sats - ?2 >=
  CASE WHEN quote_until > unixepoch() OR ?3 = 1 THEN -1000 ELSE 0 END)
RETURNING allowance_calls, balance_sats;
-- no row returned: issue the 402 and open the window
UPDATE credit_accounts SET quote_until = unixepoch() + 120 WHERE identity_key = ?1;
-- the refund: one call's value back as credit
UPDATE credit_accounts SET balance_sats = balance_sats + ?2, calls_served = calls_served - 1,
  updated_at = unixepoch() WHERE identity_key = ?1;
-- a top-up: one batch, the PRIMARY KEY makes it once per txid
INSERT INTO credit_topups (txid, identity_key, satoshis, derivation_prefix) VALUES (?1, ?2, ?3, ?4);
UPDATE credit_accounts SET balance_sats = balance_sats + ?3, quote_until = 0 WHERE identity_key = ?2;
```

SQLite evaluates every `SET` expression on the row's old values, so the allowance test in both `CASE`s sees the same state `[SRC]` (SQLite's `UPDATE` semantics). The debit runs before dispatch so two concurrent calls cannot both spend the last 100 sats; the object's single writer gives the same guarantee without the conditional `[D]`.

**The refund, precisely.** A call is not debited when its method fails: when dispatch returns a JSON-RPC `error` object (any code), or the Worker answers 5xx after the debit, the refund statement commits before the answer is signed. The refund is 100 sats of credit whether the debit took an allowance call or balance: equal in value at the list price, and the statement needs no memory of which `[D]`. A refund that fails to commit writes one `monitor_events` row (`credit_refund_fault`, the identity, the request nonce) for the operator's manual credit; the scoreboard's target for that row is 0. A Worker that dies between debit and refund loses the payer 100 sats; the object home narrows this to the object's own crash `[D]`.

**The cut-over.** Per wallet, #28's migration copies the `credit_accounts` row and that identity's `credit_topups` rows into the object inside the migration's digest; the door reads the home the directory names for the wallet; the D1 rows are frozen at the wallet's move and deleted after the 30-day recovery window (DECISIONS section 3) `[D]`.

## 3. The claims

The crate's table (`payment_claims.rs:27-30`) in the global D1 `DB`, the owner's word for the claims' home: `nonce TEXT PRIMARY KEY, agent, created_at, txid, released`. `D1PrefixStore(&db)` takes the handle (`:112`), so no `CLAIMS` binding is needed (`payment_prefix_gate` reads `env.d1("CLAIMS")`, `:284`); the door maps `PrefixClaim` by the crate's fleet table (`:11-18`). The feature `d1-claims` turns on (`Cargo.toml:26-27` today says the opposite).

**The UNIQUE on txid** (here, in the migration, and in the crate): `CREATE UNIQUE INDEX IF NOT EXISTS payment_claims_txid ON payment_claims(txid) WHERE txid IS NOT NULL;`. Today the claim's upsert on a new prefix with a known txid would raise a constraint error, which the batch reports as a fault, so 503 instead of a replay (`payment_claims.rs:150-185`) `[D]`. Hence the crate issue:

> **payment_claims: a UNIQUE on txid answered as a replay, one spelling of the invalid-payment code, a prune helper, a public challenge builder**
> The reference keys BRC-105 replay claims by transaction id (`KnexPaymentReplayStore.ts:18-47` at ts-stack edf6e03, `payment_replays`, duplicate insert refused). `payment_claims` keys by prefix only. Asked: (1) `PAYMENT_CLAIMS_MIGRATION` gains `CREATE UNIQUE INDEX IF NOT EXISTS payment_claims_txid ON payment_claims(txid) WHERE txid IS NOT NULL`, and `claim_payment_prefix` classifies that constraint as `SameTransaction` (409 `ERR_PAYMENT_REPLAYED`), never as a fault; (2) one spelling: the claims gate and the verify docs say `ERR_PAYMENT_INVALID` (`payment_claims.rs:16, 243`; `payment_verify.rs:36-39`) where `error.rs:167` and the reference (`index.ts:323`) say `ERR_INVALID_PAYMENT`; (3) `prune_payment_claims(db, older_than_secs, limit)` with the doc's "bindings never expire" (`:4`) amended to state the host's later guards; (4) `challenge_header_pairs` (`payment.rs:894`) public, so a door with its own internalizer emits the exact set. Witness: a native test per item; the conformance suite unchanged. Wanted by wallet-infra #24.

**The expiry.** 365 days, the reference's (`KnexPaymentReplayStore.ts:22, 44-46`). The crate keeps bindings forever because the HMAC never expires (`payment.rs:150-151`); pruning is safe here because two guards outlive the claim: the operator's `isMerge` on a known txid (`internalize_action.rs:427-428`) and `credit_topups.txid` as PRIMARY KEY `[D]`. The cron (every five minutes, `wrangler.toml:86`), on its run at minute 0 of each hour: `DELETE FROM payment_claims WHERE rowid IN (SELECT rowid FROM payment_claims WHERE created_at < unixepoch() - 31536000 LIMIT 500);`. At today's load about 560 claims a month (1,876 x 30 / 100) `[EST]`.

## 5. The public shape

**The price page** (text for the keeper to publish, rule 14):

> Wallet storage on Cloudflare. Every identity starts with 1,000 calls free. After that a call costs 100 satoshis, paid in advance: when your credit runs out the server answers with a standard BRC-105 402 asking 10,000 satoshis, which your wallet pays by itself (100 calls of credit). The connection handshake, the settings reads and the calls that release a reservation are free; a batch commit costs one call per action; a call that fails is not charged; a deposit is never refused for lack of credit. Payments go to the server's identity key; credit is not refundable in coin and does not expire. Prices may change with 30 days' notice on this page.

**The 402 is the quote**: its headers and body (section 1) are the whole tariff a client needs; no other endpoint carries a price.

**The terms line**: "Credit buys calls at the posted price; it is not a deposit, carries no interest and is not redeemable for coin; the operator keeps the right to refuse abuse under the posted rate limits." (the keeper's and the owner's words, rule 14).
